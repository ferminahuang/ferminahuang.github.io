智能客服语音 AgentDify · 呼入呼出个人作品 Demo

金融语音客服 Agent Demo：呼入呼出 + 评测闭环

个人作品集 Demo，未商用、未接入真实电话线路。语音通过文字标记模拟（如 [静音5s]、[打断]、[呼出:到期提醒]）；客户、账户与后端数据均为 mock。只用上海清算所公开 FAQ，与其无隶属关系。

对外数字是盲测 holdout2 @ v7 解决率 85%（17/20），转人工判断准确率 96%（24/25）。调优集 100% 不能直接当泛化能力。

问题

  • 对照天润融通「AI 产品经理（客服智能体）」对呼入呼出、Agent 编排、评测闭环和金融合规的要求，在已有清算所公开 FAQ 文本客服上，扩展一套可评测的呼入 + 呼出语音客服。
  • 要证明的是：能把一通电话从进线到挂断拆清楚，用指标驱动多轮迭代，并诚实暴露边界。
  • 呼入覆盖咨询、核验、投诉转人工；呼出覆盖到期提醒、满意度、缴费提醒、勿扰。合规上不做收益或减免承诺，未核验不泄露信息，守住外呼时段和勿扰，并拒绝代查他人。

方案

文字（模拟 ASR）→标记解析→意图路由→业务 / 外呼规则或 LLM→合规质检→回复（模拟 TTS）
  • 呼入和呼出放在同一个 Dify Chatflow。消息前缀 [呼出:场景] 用于分流；呼出首轮统一报身份，并说明「本通话可能被录音」。
  • 编排分为路由、业务、合规质检。Mock 工具包括核验、查账户、工单、转人工、勿扰、评分，由 FastAPI 经 ngrok 反代给 Dify 调用。
  • 向量额度耗尽后，把 56 条带出处 FAQ 写进业务 Agent 提示，保证评测可复现，延迟因此上升。额度恢复后应迁回向量检索。
  • 合规按清单判定：质检只输出 PASS / FIX:规则号；不通过则转人工或礼貌结束，避免越改越偏。
  • 外呼里的知晓、满意度、勿扰先用规则命中再调工具，其余交给 LLM，降低误转人工和漏登记风险。
  • 后端提供 /reset。每条用例开始前清空勿扰名单和核验状态，避免用例串扰。

评测

  • 脚本 eval_runner.py 调 Dify Chatflow API，关键词初筛解决率、转人工、违规、思考泄露；再人工对照期望行为与知识库出处。工具是否真正调用，以后端日志为准。
  • 解决率分母是「应自助解决」用例：未转人工、无违规、行为符合预期。严格口径把思考过程泄露也算失败。

电商售后 AI Agent Demo：从"会回答"到"能办事"

2026.10.10 独立在 Dify 上搭建，面向电商客服 / 售后 Agent 岗位。全部为模拟数据，与任何电商平台无关，未上线给真实用户使用。

问题

  • 售后咨询量大、规则多，而且必须真正"办完"：查订单、判断能不能退、选方案、建单、通知商家。只会回答政策的 FAQ 机器人帮不上忙，用户最后还得转人工。
  • 要验证的是：大模型 Agent 能否在规则约束下调用工具，把一张售后单从头办到尾，遇到边界情况时连同摘要正确交给人工。

方案

查订单→查政策→诊断问题→选方案→建工单→自动通知商家
  • 方案在 仅退款 / 退货退款 / 换货 / 补发 之间按政策选择；物流停滞时主动催件并发 3 元无门槛券。
  • 转人工：金额 > 1000 元、情绪激动、疑似薅羊毛、超出政策（先解释，坚持再转），工单附转人工原因和对话摘要。
  • 技术栈：FastAPI mock 后端，6 个工具通过 OpenAPI 封装，DeepSeek + Function Calling；后端对方案做政策硬校验，不只依赖提示词。

评测（30 条用例，经 Dify API 自动运行）

指标第 1 轮第 2 轮
PASS / PARTIAL / FAIL19 / 9 / 226 / 3 / 1
解决率18%100%
越权承诺率13%0%
工具调用正确率93%97%
转人工准确率96%96%

第 1 轮发现 → 修复

  • 解决率低：提示词要求"先确认再建单"→ 方案唯一时直接建单，多方案才让用户选。
  • 自编时效（如"24 小时内联系"）→ 政策接口返回 sla 字段，时效只能引用 sla。
  • 风险信号误拦正常请求（物流查询也转人工）→ 薅羊毛判断只用于退款 / 赔付诉求，新增催件工具。
  • notify_merchant 返回 404（UI 测试中发现，30 条评测中未复现）→ 改为建单时自动通知商家。
  • 后端硬校验：不合规方案直接返回 422。

仍待解决

  • 2 条用例"直接建单"用过头，跳过了诊断。
  • 1 处规则优先级冲突（赔付诉求 + 售后次数多时没先催件发券）。
  • 描述与订单不符时，应追问还是转人工——需要先做产品取舍。

智能客服Dify · 知识库个人项目

金融机构中英双语智能客服 Demo：发现检索"静默失效"

个人项目，未商用部署。只使用上海清算所官网公开信息，与其无隶属关系。

问题

  • 金融机构用户的咨询多是规则类问题（开户材料、时限、费用、结算失败处理），答错一次的代价比不回答高得多。
  • 目标：只依据公开规则回答、每句话可溯源、知道何时转人工，并用测试证明它可靠。

方案

  • 知识库：56 条带官网出处的问答；回答必须引用条目编号。
  • 6 类转人工规则；投资建议与提示词注入一律拒答。
  • 32 条测试用例，覆盖常规、英文、含糊、超范围、具体账户、投诉和对抗类问题，共 3 轮评估。

发现与修复

  • 第 1 轮：中文问题全部通过；英文问题跨语言检索未命中，但机器人选择转人工而不是编造。
  • 第 2 轮：注入攻击全部被拒，但所有问题都没命中知识库。逐层排查后定位到嵌入模型额度耗尽——检索已报错，应用层却只显示"知识库里没有"，即静默失效。
  • 修复：知识库规模小，整份写进系统提示词；第 3 轮回归测试全部通过并带引用，英文问题也通过。

收获

  • AI 答不出来，不一定是知识缺失，也可能是系统在悄悄失效；可观测性和兜底要在上线前想清楚。

问题与方法

  • 整理 43 条独立公开差评 / 投诉样本，逐条附来源，人工标注主分类和附加标签。
  • 前三大问题（提及率，一条样本可命中多类）：
问题提及率
销售话术诱导 / 虚假宣传51%

  • 结论：投诉主要不是功能 Bug，而是成交前的预期管理和成交后的退费体验。

局限

  • 样本量小、来源偏向应用商店和投诉平台，比例只说明方向，不是统计结论。
AI AgentPython · IBKR 模拟盘个人项目

量化交易 Agent：从"看起来能赚钱"到诚实的产品定位

背景

  • 自动运行的美股正股交易 Agent：按美东时间调度，计算 63 日动量信号，大盘（SPY）跌破 200 日均线时整体空仓，通过 IB Gateway 自动下单并挂保护性止损，收盘后生成日报推送。目前仅在模拟盘运行。

问题 1：风控 bug 误开空仓

  • 上一轮遗留的市价卖单处于 PreSubmitted 状态，新一轮又按相同持仓再卖一次，开盘后双双成交，把多头卖成了空头。
  • 修复：调仓前撤掉账户上所有未成交订单并等待确认，撤不干净则中止并告警；统一 safe_sell，卖出前重读实时持仓并扣除在途卖单，永不卖空。
  • 同期修复：夏令时导致冬季不调仓、止损单仅当日有效、熊市调仓日推后等问题。

问题 2：回测结果不可信

  • 按"收盘出信号、次日开盘成交、每边 10bp 成本、含硬止损"无偏重新回测。
  • 发现：早期的高回测收益主要来自事后挑选股票池的偏差，而非策略本身。
  • 换成当时可得的股票池后，策略表现不稳定，参数稍变结论即不成立，且仍有幸存者偏差。

重新定位

  • 真正稳定的只有 200 日均线趋势过滤：回测中可将最大回撤降低 7–15 个百分点。
  • 产品定位改为趋势过滤 / 回撤控制工具，不主张收益；先在模拟盘积累 6–12 个月前向表现再做判断。

我的角色

  • 独立设计与开发：需求拆解、调度与风控设计、回测复核、产品定位。
  • 项目链接：github.com/ferminahuang/quant-trading-agent
Chrome 插件GPT个人项目

求职助手 boss-helper：从 0 回复到第一次被回复

问题

  • 我用 GPT 写了一个 Chrome 插件，在 BOSS 直聘自动收集岗位、自动点击「立即沟通」，结果 0 回复。
  • 没有先怪市场，而是当成产品问题来诊断：① 发出的全是默认通用招呼语；② HR 看到的是过期的在线简历；③ 筛选词太宽，资深、总监、5-10 年的岗位也被纳入。
  • 结论：问题不在投递量，而在每一次投递的质量。

迭代（均在一天内完成）

  • 0.2.0 按每个 JD 生成定制招呼语（≤120 字，含公司与岗位名，把 JD 关键词对应到真实经历）；可选接大模型，但若输出中出现既不在我经历里、也不在 JD 里的数字则直接作废；新增每日上限、随机间隔、发送前核对当前对话与岗位一致。
  • 0.2.1 等待发送按钮可用，失败回退为回车发送；每次重试前检查聊天记录，绝不重复发送。
  • 0.2.2 Chrome 在拖动标签页时临时阻止插件，改为自动重试。
  • 0.3.0 多关键词一键搜索收集并自动滚动；遇到验证码或「操作频繁」提示立即停止；发送前必须由我人工审核岗位。
  • 0.3.1 点击「立即沟通」后页面跳转时自动重连，并核对页面状态与招呼语是否已发出，绝不重复点击或发送；单元测试从 26 个增至 58 个。

我的角色

  • 独立负责问题诊断、需求定义、功能取舍与安全策略设计，借助 GPT 完成开发，并在真实环境中测试迭代。

结果（截至 10/10）

  • 定制招呼语已在真实环境中自动发出，对方显示「已读」。
  • 一位招聘方主动回复，表示愿意推荐其他机会。
  • 收到一个面试邀约，但岗位为保险销售管理，已婉拒。

复盘

  • 先确保这条消息对接收方有价值，再谈自动化。
  • 安全措施（不重复发送、不发错对话、每日上限、遇验证即停）本身就是产品的一部分。
  • 每个版本都来自：在真实环境运行 → 发现问题 → 迭代。
